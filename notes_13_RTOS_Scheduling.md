# Lecture 13: Real-Time Operating Systems (RTOS) Scheduling

## Overview

This lecture covers Real-Time Operating Systems (RTOS) and their scheduling mechanisms. RTOSs are specialized operating systems designed for embedded systems that must guarantee predictable timing behavior and meet hard deadlines. The lecture introduces fundamental concepts of task management, scheduling algorithms, and the challenges of real-time scheduling in embedded systems.

---

## Technical Terms & Definitions

**Operating System (OS)**
- Software layer that manages hardware resources and provides services to applications
- Handles multitasking, resource sharing, peripheral access, and user interfaces
- Abstracts hardware complexity from applications

**Real-Time Operating System (RTOS)**
- Operating system designed specifically for real-time applications
- Guarantees predictable timing behavior and deadline satisfaction
- Focuses on determinism over throughput or fairness

**General-Purpose Operating System**
- OS designed for desktop/server environments (Windows, Linux, macOS)
- Optimized for fairness and responsiveness across many tasks
- Not suitable for hard real-time requirements due to timing uncertainty

**Embedded Operating System**
- OS designed specifically for embedded systems
- Typically lean, configurable, and optimized for specific hardware
- Focus on predictability, low overhead, and real-time capabilities

**Multitasking / Quasi-Parallelism**
- Running multiple processes or threads concurrently on a single processor
- Creates illusion of parallel execution through rapid context switching
- Only one task actually executes at any given moment on single-core systems

**Task / Thread / Process**
- Independent unit of execution with its own execution context
- Thread: Lightweight, shares memory with other threads in same process
- Process: Heavyweight, has its own isolated memory space
- In RTOS context, often used interchangeably

**Context Switch**
- Process of saving the state of a running task and restoring the state of another task
- Includes saving/restoring CPU registers, program counter, stack pointer
- Takes time (overhead) - typically a few hundred clock cycles

**Process Control Block (PCB)**
- Data structure containing all information about a task
- Includes: process state, process ID, program counter, CPU registers, memory regions, stack/heap locations, priority, scheduling information
- OS maintains PCBs for all tasks in the system

**Preemption**
- Forcibly interrupting a running task to allow another task to run
- Triggered by system tick (timer interrupt) in RTOS
- Preempted task unaware of interruption, expects context restored when resumed
- Essential for priority-based real-time scheduling

**System Tick**
- Regular timer interrupt generated by hardware timer
- Provides periodic "heartbeat" for the scheduler (e.g., every 1ms or 10μs)
- Triggers preemption and allows OS to reassess task priorities
- Frequency determined by application requirements and overhead tolerance

**Interrupt Service Routine (ISR)**
- Special function executed in response to hardware interrupt
- Handles time-critical interrupt processing
- Should be kept short to minimize interrupt latency
- Can trigger task state changes (e.g., unblocking waiting tasks)

**Interrupt**
- Asynchronous event triggered by hardware or software
- Can occur at any time during program execution
- Causes context switch to ISR
- Usually returns to same task after handling (unlike preemption)

**Scheduler**
- Component of OS that decides which task to run next
- Implements scheduling policy (e.g., RMS, EDF, priority-based)
- Invoked on: task completion, task blocking, preemption, task creation/deletion
- Critical for meeting real-time deadlines

**Scheduling Policy / Algorithm**
- Rules determining which task runs when multiple tasks are ready
- Examples: Round-Robin, Priority-based, Rate Monotonic, Earliest Deadline First
- Choice depends on application requirements and deadline guarantees needed

**Task State**
- Current status of a task in the system
- Three primary states: Running, Ready, Blocked
- State transitions triggered by scheduler, task actions, or events

**Running State**
- Task currently executing on the CPU
- Only one task can be running at a time (single-core)
- Can transition to Ready (preempted) or Blocked (waiting)

**Ready State**
- Task ready to execute but waiting for CPU
- Stored in ready queue, ordered by scheduler's policy
- Transitions to Running when selected by scheduler (dispatch)

**Blocked State**
- Task waiting for an event or resource
- Not eligible for CPU time
- Transitions to Ready when event occurs or resource becomes available
- Examples: waiting for I/O, semaphore, timer expiration

**Dispatch**
- Act of scheduler selecting next task from ready queue and starting its execution
- Involves restoring task's context from PCB
- Part of context switch overhead

**Deadline (d)**
- Time by which a task must complete its execution
- Critical constraint in real-time systems
- Can be hard (must never miss) or soft (occasional miss tolerable)

**Arrival Time / Release Time (a)**
- Time when a task becomes ready for execution
- For periodic tasks: arrival times occur at regular intervals
- First arrival time called "phase" (Φ)

**Computation Time / Execution Time (C)**
- Amount of CPU time a task needs to complete
- Must be known or bounded for schedulability analysis
- Represents worst-case execution time (WCET) for safety-critical systems

**Start Time (s)**
- Time when a task actually begins execution
- May differ from arrival time if CPU is busy

**Finishing Time (f)**
- Time when a task completes its execution
- Used to calculate lateness and other metrics

**Period (T)**
- Time interval between successive activations of a periodic task
- For periodic task, arrival times: a, a+T, a+2T, a+3T, ...
- Deadline typically equals period: d = T

**Phase (Φ)**
- Activation time of the first instance of a periodic task
- Offset from time zero
- Tasks with zero phase are synchronous (critical moment)

**Lateness (L)**
- Difference between finishing time and deadline: L = f - d
- Can be negative (finished early) or positive (missed deadline)
- Metric for how well deadlines are met

**Tardiness / Exceeding Time (E)**
- Time a task executes after its deadline: E = max(0, L)
- Always non-negative (zero if deadline met)
- Critical metric for deadline misses

**Slack Time (X)**
- Maximum time a task can be delayed before starting and still meet deadline
- Formula: X = d - a - C
- Indicates scheduling flexibility

**CPU Utilization (U)**
- Fraction of CPU time used by tasks
- For single task: U = C / T
- For task set: U = Σ(Ci / Ti)
- Expressed as percentage (e.g., 75%)

**Schedulability**
- Property indicating whether all tasks in a set can meet their deadlines
- Task set is schedulable if a feasible schedule exists
- Depends on: CPU utilization, scheduling algorithm, task characteristics

**Feasible Schedule**
- Schedule where all tasks meet their deadlines
- Existence depends on task parameters and scheduling algorithm
- Schedulability analysis determines if feasible schedule exists

**Critical Section**
- Code segment accessing shared resources
- Must execute atomically (no interleaving with other critical sections)
- Protected by synchronization mechanisms (semaphores, mutexes)

**Semaphore**
- Synchronization primitive for protecting critical sections and coordinating tasks
- Binary semaphore: 0 (locked) or 1 (unlocked)
- Counting semaphore: arbitrary non-negative integer
- Operations: P (wait/take) and V (signal/give)

**Interprocess Communication (IPC)**
- Mechanisms for tasks to exchange data and coordinate
- Includes: shared memory, message queues, pipes, semaphores, signals
- RTOS integrates IPC with scheduling to prevent deadlocks

**Middleware**
- Software layer between application and OS
- Provides higher-level services (e.g., handling multiple tasks accessing same device)
- Abstracts complexity from application developers

**Device Driver**
- Software controlling hardware peripherals
- In embedded OS: often handled by tasks rather than kernel
- More predictable timing when scheduler manages driver access

**Real-Time Clock**
- Hardware timer generating system ticks
- Provides time base for scheduler
- Enables timed task execution and periodic behavior

**Predictability / Determinism**
- Ability to predict worst-case timing behavior
- Essential requirement for RTOS
- Requires bounded execution times for all operations (tasks, ISRs, system calls)

**Latency**
- Delay between event occurrence and response
- Interrupt latency: time from interrupt to ISR execution
- Scheduling latency: time from task ready to task running
- Must be bounded and guaranteed in RTOS

**Hard Real-Time**
- System where missing a deadline is catastrophic
- Requires formal verification of timing guarantees
- Examples: airbag deployment, flight control, medical devices

**Soft Real-Time**
- System where occasional deadline misses are tolerable
- Performance degrades gracefully with deadline violations
- Examples: multimedia streaming, network packet processing

**Firm Real-Time**
- System where late results have zero value but no catastrophic consequences
- Result worthless if deadline missed
- Examples: video frame processing

**Non Real-Time**
- No timing constraints or deadlines
- Performance measured by average response time or throughput
- Examples: batch processing, background maintenance tasks

**Configurability**
- Ability to include/exclude OS features based on application needs
- Essential for keeping RTOS lean and predictable
- Allows removing unused functionality to reduce overhead

**Priority**
- Numerical value determining task importance for scheduling
- Higher priority tasks preempt lower priority tasks
- Can be fixed (static) or dynamic based on scheduling algorithm

**Fixed Priority Scheduling**
- Each task assigned fixed priority that never changes
- Simple and predictable
- Example: Rate Monotonic Scheduling (RMS)

**Dynamic Priority Scheduling**
- Task priorities change during execution based on system state
- More flexible, can achieve higher CPU utilization
- Example: Earliest Deadline First (EDF)

**Rate Monotonic Scheduling (RMS)**
- Fixed priority algorithm where shorter period = higher priority
- Optimal for fixed-priority scheduling
- Guarantees schedulability up to ~69% CPU utilization
- Simple rules, fully analyzable

**Earliest Deadline First (EDF)**
- Dynamic priority algorithm where closest deadline = highest priority
- Optimal for preemptive scheduling
- Can utilize 100% CPU while meeting deadlines (theoretically)
- Higher overhead due to priority recalculation

**Priority Inversion**
- High-priority task blocked by low-priority task holding needed resource
- Can cause deadline misses
- Solutions: Priority inheritance, priority ceiling protocols

**Deadline Monotonic Scheduling (DM)**
- Fixed priority algorithm where shorter deadline = higher priority
- Generalization of RMS for tasks where deadline ≠ period
- Optimal for fixed priorities when D ≤ T

**Extended Interrupt Handling**
- Technique where ISR triggers a task to handle non-critical processing
- ISR handles only time-critical part (short)
- Task handles remaining work (can be scheduled normally)
- Uses semaphore to unblock handler task

**Aperiodic Task**
- Task with irregular, unpredictable arrival pattern
- No fixed period
- Arrival time unknown in advance
- Harder to analyze for schedulability

**Sporadic Task**
- Aperiodic task with minimum inter-arrival time
- Bounded arrival rate enables schedulability analysis
- Treated similarly to periodic tasks with period = minimum inter-arrival time

**Response Time**
- Time from task arrival to task completion: Response = f - a
- Important metric for system responsiveness
- Average response time common metric for non-real-time systems

**Idle State**
- Special low-power state when no tasks are ready
- CPU can enter sleep mode to save energy
- Wakes on next interrupt (timer tick or external event)

**Context**
- Complete execution state of a task
- Includes: CPU registers, program counter, stack pointer, stack contents
- Must be saved on preemption, restored on resumption

**Memory Protection**
- Hardware/software mechanism preventing tasks from accessing each other's memory
- Common in general-purpose OS for security
- Often omitted in embedded systems if all software trusted
- Memory Protection Unit (MPU) provides hardware support

**Cooperative Scheduling**
- Task explicitly yields CPU (calls wait/delay function)
- No preemption by timer
- Simple but one misbehaving task can block system

**Preemptive Scheduling**
- Scheduler can forcibly interrupt running task
- Required for priority-based real-time scheduling
- Ensures high-priority tasks get CPU quickly

**Kernel**
- Core part of OS managing scheduling, task management, basic IPC
- In RTOS: minimal, focuses on scheduling and synchronization
- Larger OS kernels include device drivers, file systems, networking

**Critical Moment**
- Time when all periodic tasks are ready simultaneously
- Worst-case scenario for schedulability
- Occurs at time zero when all tasks have phase Φ = 0
- Scheduling analysis typically starts at critical moment

**Hyperperiod**
- Least common multiple (LCM) of all task periods
- Time after which task arrival pattern repeats
- Schedule must be verified up to hyperperiod for complete analysis

**Cost Function / Utility Function**
- Function assigning value to task completion time
- Different shapes for different task types (hard, soft, firm, on-time)
- Used to evaluate scheduling quality for soft real-time systems

**Cumulative Value**
- Sum of utility functions over all completed tasks
- Performance metric when tasks have utility functions
- Goal: maximize cumulative value

## Core Concepts

### 1. Purpose and Functionality of Operating Systems

**Core OS Functions:**
- **Hardware Resource Management**: Allocate CPU, memory, peripherals among competing tasks
- **Multitasking**: Create illusion of parallel execution through time-sharing
- **Device Access**: Provide standardized interface to peripherals via drivers
- **User Interface**: Enable user interaction (GUI, CLI, etc.)
- **Memory Protection**: Isolate tasks to prevent interference

**Why Embedded Systems Need OS:**
- Many parallel tasks requiring coordination
- Many hardware resources to be shared
- Complex functionality requirements (medical, aerospace, automotive)
- Broad feature range (smartphones, IoT devices)
- Critical applications needing structure and verification (ABS, flight control)

**Why NOT General-Purpose OS:**
- Too many unused features consuming memory and CPU
- Not configurable - all functionality integrated
- Not designed for critical applications
- Excessive timing uncertainty - fair time-sharing unsuitable for hard deadlines
- General-purpose OS gives all tasks roughly equal CPU share for responsiveness
- Embedded systems often need specific tasks to always meet deadlines

### 2. Real-Time OS Requirements and Characteristics

**Three Essential RTOS Requirements:**

**1. Predictable Timing:**
- Upper bound on execution time must be known for all tasks
- Upper bound on ISR execution time must be known
- Upper bound on OS service call time must be known
- Guaranteed maximum latency for interrupts and scheduling
- No unbounded operations (e.g., no unlimited search times)

**2. Meeting Deadlines:**
- Scheduler must be aware of task deadlines
- Scheduling decisions based on deadline constraints
- System designed to guarantee deadline satisfaction

**3. Managing Priorities:**
- Handle both hard and soft real-time requirements
- Priority-based scheduling to ensure critical tasks run first
- Only a lean, minimal OS can guarantee hard deadlines → configurability essential

**Configurability:**
- Ability to remove unneeded OS features
- Reduces code size and complexity
- Improves predictability by eliminating unnecessary code paths
- Enables system to meet hard deadlines

### 3. Embedded OS Architecture Differences

**Embedded OS Architecture:**
- Drivers typically handled by application tasks
- Kernel focuses primarily on scheduling
- More predictable: scheduler directly manages hardware access
- Complexity: Multiple tasks accessing same device need coordination (middleware)

**General-Purpose OS Architecture:**
- Drivers integrated into kernel or as kernel modules
- Operating system layer between middleware and drivers
- More abstraction but less predictable timing

**Trade-offs:**
- Embedded: Better predictability, more development complexity
- General-purpose: Easier development, worse predictability

### 4. Embedded OS Special Features

**Task-Level Interrupts:**
- Every task can potentially handle interrupts
- Environment well-defined and filtered
- Would be unreliable in general-purpose OS (untrusted applications)
- Software written specifically for controlled environment

**Direct Task Start from Interrupts:**
- Task start address stored in interrupt vector table
- Allows faster reaction times
- No intermediate interrupt handler needed
- Enables very low-latency response to events

**Optional Protection Mechanisms:**
- If only tested software present, protection may be unnecessary
- Software considered reliable in embedded context
- Safety/security-critical systems still need protection
- Trade-off: Updates difficult to distribute if security enforced

### 5. Task States and State Machine

**Three-State Model:**

```
        Running
           ↑ ↓
   dispatch   preempt
           ↓ ↑
    Ready ← signal ← Blocked
           wait →
```

**Running State:**
- Only one task running at a time
- Task blocks when needs to wait (calls wait() function)
- Scheduler can preempt task (forced context switch)

**Ready State:**
- Queue of tasks waiting for CPU
- Scheduler selects next task (dispatch operation)
- Entry conditions: Created, preempted, or unblocked

**Blocked State:**
- Waiting for resource or event
- Not eligible for CPU time
- System tick can transition task to ready (timer expiration)
- Resource becoming available transitions to ready (signal)

**State Transition Triggers:**
- wait: Running → Blocked (task calls wait/delay/semaphore take)
- signal: Blocked → Ready (event occurs, resource available)
- dispatch: Ready → Running (scheduler selection)
- preempt: Running → Ready (higher priority task or time quantum expired)

### 6. Process Control Block and Task Context

**PCB Contents:**
- Process state (Running/Ready/Blocked)
- Process ID (unique identifier)
- Program counter (current instruction address)
- CPU registers (general-purpose and special registers)
- Priority and scheduling parameters
- Accounting information (CPU time used, etc.)
- Memory region information
- Stack pointer and stack location
- Heap location

**Processes vs Threads:**
- **Process**: Has own memory space, multiple threads possible
- **Thread**: Shares memory within process, own stack and registers
- **Thread advantages**:
  - Faster context switch (less state to save/restore)
  - Less OS intervention for thread switching
  - Shared memory enables easy communication

**Multiple Threads:**
- Process has one PCB with multiple thread control blocks
- Threads share: memory regions, heap, peripheral access
- Threads have separate: stacks, registers, program counters

### 7. Preemption Mechanism

**Preemption Flow:**
1. Timer generates interrupt (system tick)
2. ISR: vPreemptiveTick() executed
3. portSAVE_CONTEXT saves current task state
4. portRESTORE_CONTEXT loads next task state
5. vTaskSwitchContext selects next task
6. New task starts/resumes execution

**Key Characteristics:**
- System tick triggers preemption periodically
- Context switch takes time (save/restore overhead)
- Task unaware of preemption - expects context unchanged
- Transparent to application code

**Context Switch Overhead:**
- Storing context: Save CPU registers, PC, stack pointer
- Selecting next task: Scheduler decision logic
- Restoring context: Load new task's saved state
- Typically hundreds of clock cycles
- Must be much shorter than task periods

### 8. Preemption vs Interrupts

**Preemption (Timer-based):**
- Caused by system tick (regular hardware timer interrupt)
- ISR performs scheduling and context switch
- Switches to next ready task from queue
- Predictable, periodic occurrence

**Interrupt (Event-based):**
- Caused by external sources at any time
- Asynchronous event
- Causes context switch to ISR
- Execution usually returns to same task after ISR completes

**Common Characteristics:**
- Both involve context switch
- Running task has no way of knowing when switch will occur
- Must be transparent to task

**Problems This Creates:**
- Tasks cannot use simple flag variables for synchronization
- Need atomic operations and proper synchronization primitives
- Critical sections must be protected

### 9. Interprocess Communication

**Semaphore Mechanism:**
- Signal to prevent entry into critical section if resource busy
- Protects shared resources from concurrent access
- Binary semaphore: available (1) or taken (0)
- Counting semaphore: tracks multiple instances of resource

**Extended Interrupt Handling Pattern:**
1. Task J2 starts, tries to take semaphore token, blocks (no token available)
2. Normal operation: J1 running
3. IRQ occurs: ISR executes
4. ISR resets IRQ source, adds token to semaphore
5. J2 unblocked, becomes ready
6. Next system tick: scheduler preempts J1, J2 runs
7. J2 processes event, completes, calls wait()

**Advantages:**
- ISR kept minimal (only time-critical operations)
- Complex processing done in task context (can be scheduled)
- Better system responsiveness
- Avoids long ISRs that block other interrupts

### 10. Timed Execution

**Problem with delay():**
```c
while (true) {
    // Work takes time t_work
    delay(200ms);  // Adds 200ms
}
// Period = t_work + 200ms (not exactly 200ms!)
```

**Solution with delayUntil():**
```c
Time lastWake = now();
while (true) {
    // Work takes time t_work
    delayUntil(&lastWake, 200ms);  // Next wake = lastWake + 200ms
}
// Period = exactly 200ms
```

**Difference:**
- `delay()`: Delays from current time (period drifts)
- `delayUntil()`: Delays from last wakeup time (maintains period)
- OS tracks last wakeup time for periodic execution
- Critical for maintaining precise periodic behavior

### 11. Priority-Based Scheduling

**Equal Priorities:**
- System tick preempts current task
- Tasks alternate execution (round-robin within priority level)
- Fair time distribution among equal-priority tasks

**Different Priorities:**
- Higher priority task always runs first when ready
- Lower priority tasks only run when higher priority tasks blocked
- Idle task runs when all application tasks blocked
- Scheduler goes to low-power idle mode for energy saving

**Priority Assignment:**
- Application defines task priorities at creation
- Priority determines order in ready queue
- Scheduler always dispatches highest-priority ready task

### 12. Scheduling Terminology and Metrics

**Task Parameters:**
- **ai**: Arrival/release time (when task becomes ready)
- **Ci**: Computation time (CPU time needed)
- **di**: Deadline (must finish by this time)
- **si**: Start time (when actually starts executing)
- **fi**: Finishing time (when completes)
- **Ti**: Period (for periodic tasks)
- **Φi**: Phase (first arrival time)

**Derived Metrics:**
- **Lateness**: Li = fi - di (can be negative)
- **Tardiness**: Ei = max(0, Li) (always ≥ 0)
- **Slack**: Xi = di - ai - Ci (maximum delay before start)

**System Metrics:**
- **Average response time**: (1/n) Σ(fik - aik)
- **Total completion time**: max(fi) - min(ai)
- **Maximum lateness**: max(fi - di)
- **Number of late tasks**: Σ miss(fi)

**Real-Time Systems Metrics:**
- Maximum lateness most relevant (worst-case)
- Number of late tasks for firm real-time
- Average metrics less relevant (care about worst-case)

### 13. Scheduling Cost Functions

**Four Task Types:**

**1. Non Real-Time:**
- No deadline
- Constant value regardless of completion time
- No timing constraints

**2. Soft Real-Time:**
- Non-critical deadline
- Value decreases gradually after deadline
- Early termination acceptable
- Examples: video streaming, UI responsiveness

**3. On-Time:**
- Finishing close to deadline maximized value
- Value decreases before and after deadline
- Example: Audio sample playback

**4. Hard/Firm Real-Time:**
- System worthless if deadline missed
- Value drops to zero at deadline
- Hard: catastrophic if missed
- Firm: no value but no catastrophe

**Cumulative Value:**
- Sum of utility functions for all tasks
- Performance metric for soft real-time systems
- Goal: Maximize total value delivered

### 14. Rate Monotonic Scheduling (RMS)

**Assumptions:**
- All threads run on single CPU
- Context switch time = 0 (negligible)
- Threads independent (no resource sharing)
- Constant computation time per thread
- Deadline = end of period (Di = Ti)
- Shorter period → higher priority
- Highest-priority ready process runs

**Priority Assignment:**
- Fixed priorities based on period
- T1 < T2 → Priority(Task1) > Priority(Task2)
- Optimal for fixed-priority scheduling
- If RMS can't schedule it, no fixed-priority algorithm can

**Schedulability:**
- Guaranteed up to U ≤ n(2^(1/n) - 1)
- For n → ∞: U ≤ ln(2) ≈ 0.69 (69%)
- Higher utilization: must draw schedule to verify
- Can waste up to 31% of CPU

**Advantages:**
- Simple rules
- Fixed priorities (no runtime computation)
- Fully analyzable
- Well-understood theory

**Disadvantages:**
- Conservative (wasteful)
- Only works for periodic tasks with D = T
- May fail to schedule even with U < 100%

### 15. Earliest Deadline First (EDF)

**Characteristics:**
- Dynamic priority scheduling
- Task closest to deadline gets highest priority
- Priorities recalculated at each scheduling decision
- Works for periodic and aperiodic tasks

**Schedulability:**
- Guaranteed feasible schedule if U ≤ 100%
- Optimal for preemptive scheduling
- Best possible utilization
- No CPU waste due to algorithm limitations

**Implementation:**
- On each timer interrupt:
  - Compute time to deadline for each ready task
  - Run task with closest deadline
- Generally expensive for practical use
- If system tick fine-grained, overhead significant

**Advantages:**
- Maximum CPU utilization
- Optimal algorithm
- Handles aperiodic tasks
- No artificial utilization limit

**Disadvantages:**
- High runtime overhead (priority recalculation)
- Complex implementation
- More context switches
- Assumes zero switching time (unrealistic)

### 16. Scheduling Anomalies

**Preemptive with Resource Sharing:**
- Faster CPU can cause deadline misses!
- Reason: Low-priority task reaches critical section earlier
- Blocks high-priority task longer
- Example: At slow speed, high-priority task preempts before critical section
- At fast speed, low-priority task already in critical section when high-priority arrives

**Non-Preemptive:**
- Faster CPU can cause deadline misses!
- Reason: Task ordering changes with faster execution
- Task that would arrive during execution now arrives after
- Changes which task runs first
- Can push urgent task later in schedule

**Implications:**
- Faster hardware doesn't guarantee better timing
- Resource contention creates complex interactions
- Timing analysis must consider all scenarios
- Simple speedup assumptions invalid

### 17. Real-Time Scheduling Challenges

**Context Switch Time:**
- RMS and EDF assume zero switching time
- Real systems: hundreds of clock cycles per switch
- Must ensure switching time << task periods
- Non-zero switching can break tight schedules
- Effects difficult to predict (depends on switching order)

**What If Not Schedulable:**
- Change requirements (relax deadlines)
- Reduce execution times (optimize code)
- Get faster CPU
- Use multiple CPUs (different scheduling problem)
- Redesign system architecture

**Overhead Management:**
- Keep system tick duration significantly larger than context switch time
- Balance: Fine tick → better responsiveness but more overhead
- Typical: Tick every 1-10ms, context switch ~100-500 cycles

## Formulas & Procedures

### Formula 1: CPU Utilization for Single Task

**U = C / T**

Where:
- U = CPU utilization (0 to 1, or 0% to 100%)
- C = Computation time (CPU time task needs)
- T = Period (time between task activations)

**Example:**
- Task with C = 2ms, T = 10ms
- U = 2/10 = 0.2 = 20%

### Formula 2: Total CPU Utilization for Task Set

**U_total = Σ(Ci / Ti) for i = 1 to n**

Where:
- n = number of tasks
- Ci = computation time for task i
- Ti = period for task i

**Example:**
- Task 1: C1=1, T1=3 → U1 = 1/3 ≈ 0.333 = 33.3%
- Task 2: C2=2, T2=5 → U2 = 2/5 = 0.4 = 40%
- Task 3: C3=1, T3=10 → U3 = 1/10 = 0.1 = 10%
- Total: U = 0.333 + 0.4 + 0.1 = 0.833 = 83.3%

**Interpretation:**
- U < 100%: Necessary condition for schedulability (but not sufficient for RMS)
- U > 100%: Not schedulable (CPU overloaded)
- U = 100%: Critical - schedulable only with optimal algorithm (EDF)

### Formula 3: Lateness

**Li = fi - di**

Where:
- Li = lateness of task i
- fi = finishing time of task i
- di = deadline of task i

**Interpretation:**
- Li < 0: Task finished early (negative lateness)
- Li = 0: Task finished exactly at deadline
- Li > 0: Task missed deadline (positive lateness)

**Example:**
- Task finishes at fi = 15ms, deadline di = 12ms
- Li = 15 - 12 = 3ms (missed by 3ms)

### Formula 4: Tardiness / Exceeding Time

**Ei = max(0, Li) = max(0, fi - di)**

Where:
- Ei = tardiness (always ≥ 0)
- Li = lateness

**Interpretation:**
- Ei = 0: Deadline met (or finished early)
- Ei > 0: Deadline missed by Ei time units

**Example:**
- Task A: fi=8, di=10 → L=-2 → E=max(0,-2)=0 (on time)
- Task B: fi=15, di=12 → L=3 → E=max(0,3)=3 (late by 3)

### Formula 5: Slack Time

**Xi = di - ai - Ci**

Where:
- Xi = slack time for task i
- di = deadline
- ai = arrival time
- Ci = computation time

**Interpretation:**
- Xi = maximum time task can be delayed before starting and still meet deadline
- Xi > 0: Task has flexibility in scheduling
- Xi = 0: Task must start immediately to meet deadline
- Xi < 0: Task cannot meet deadline even if started immediately

**Example:**
- Task arrives at ai=5, needs Ci=3, deadline di=12
- Xi = 12 - 5 - 3 = 4ms
- Task can be delayed up to 4ms after arrival and still finish on time

### Formula 6: RMS Schedulability Bound

**U ≤ n × (2^(1/n) - 1)**

Where:
- U = total CPU utilization
- n = number of tasks

**Interpretation:**
- If U ≤ bound: Task set is guaranteed schedulable with RMS
- If U > bound: Must verify by constructing schedule (may still be schedulable)

**Example Values:**
- n=1: U ≤ 1.000 (100%)
- n=2: U ≤ 0.828 (82.8%)
- n=3: U ≤ 0.780 (78.0%)
- n→∞: U ≤ ln(2) ≈ 0.693 (69.3%)

**Practical Use:**
- Quick test: If utilization ≤ 69%, RMS guaranteed to work
- Between 69% and 100%: Must draw schedule to verify

### Formula 7: EDF Schedulability Condition

**U ≤ 1** (for periodic tasks with Di = Ti)

Where:
- U = total CPU utilization = Σ(Ci / Ti)

**Interpretation:**
- EDF can schedule any task set with U ≤ 100%
- Optimal for preemptive scheduling
- No wasted CPU capacity due to algorithm

**Comparison with RMS:**
- RMS: Guaranteed only up to ~69%
- EDF: Guaranteed up to 100%
- EDF can schedule 31% more CPU load

### Formula 8: Response Time

**Ri = fi - ai**

Where:
- Ri = response time for task i
- fi = finishing time
- ai = arrival time

**Interpretation:**
- Total time from task arrival to completion
- Includes waiting time and execution time
- Must be ≤ deadline for hard real-time

**Average Response Time:**
**R_avg = (1/n) × Σ(fik - aik)**

- Common metric for general-purpose OS
- Less relevant for hard real-time (worst-case matters more)

### Formula 9: Period of Periodic Task

**ai,k = Φi + k × Ti** (for k = 0, 1, 2, ...)

Where:
- ai,k = arrival time of k-th instance of task i
- Φi = phase (first arrival time)
- Ti = period
- k = instance number

**Example:**
- Task with Φi=2, Ti=5
- Arrivals: a0=2, a1=7, a2=12, a3=17, ...

### Formula 10: Hyperperiod

**H = LCM(T1, T2, ..., Tn)**

Where:
- H = hyperperiod
- LCM = least common multiple
- Ti = periods of all tasks

**Interpretation:**
- Time after which task arrival pattern repeats
- Schedule repeats every hyperperiod
- Schedulability analysis needs verification up to H

**Example:**
- Tasks with periods T1=3, T2=4, T3=6
- H = LCM(3, 4, 6) = 12
- Schedule repeats every 12 time units

### Procedure 1: RMS Priority Assignment

**Steps:**
1. Identify all periodic tasks in system
2. Determine period Ti for each task i
3. Assign priorities: Shorter period → Higher priority
4. If T1 < T2 < T3, then Priority(Task1) > Priority(Task2) > Priority(Task3)
5. Priorities remain fixed during execution

**Properties:**
- Static/fixed priority algorithm
- Simple and deterministic
- Optimal among fixed-priority algorithms
- No runtime computation needed

### Procedure 2: EDF Scheduling Decision

**At each scheduling point:**
1. Compute current time t
2. For each ready task i:
   - Calculate time to deadline: (di - t)
3. Select task with smallest (di - t)
4. Run selected task until:
   - It completes, OR
   - It blocks, OR
   - A new task arrives with closer deadline
5. Repeat from step 1

**Properties:**
- Dynamic priority (recalculated at each decision)
- Optimal for preemptive scheduling
- Higher overhead than RMS

### Procedure 3: Schedulability Analysis Process

**For RMS:**
1. Calculate utilization: U = Σ(Ci / Ti)
2. Calculate bound: Ubound = n(2^(1/n) - 1)
3. If U ≤ Ubound: GUARANTEED schedulable ✓
4. If U > Ubound: Draw schedule up to hyperperiod
5. Check if all deadlines met in drawn schedule
6. If yes: Schedulable ✓, If no: Not schedulable ✗

**For EDF:**
1. Calculate utilization: U = Σ(Ci / Ti)
2. If U ≤ 1: Schedulable ✓
3. If U > 1: Not schedulable ✗

### Procedure 4: Context Switch Operations

**On Preemption (save current task):**
1. Save program counter (PC)
2. Save all CPU registers (R0-R15, etc.)
3. Save status register (flags)
4. Save stack pointer (SP)
5. Update PCB with saved state
6. Mark task as "Ready"

**On Dispatch (restore new task):**
1. Select highest-priority ready task
2. Load PCB of selected task
3. Restore stack pointer
4. Restore status register
5. Restore all CPU registers
6. Restore program counter
7. Mark task as "Running"
8. Resume execution

**Overhead:**
- Typically 100-500 CPU cycles
- Must be << system tick period
- Non-preemptive code reduces switches

## Comparisons & Contrasts

### Comparison 1: RTOS vs General-Purpose OS

| Aspect | RTOS | General-Purpose OS |
|--------|------|-------------------|
| **Goal** | Meet deadlines, predictability | Fairness, throughput, user experience |
| **Scheduling** | Priority-based, deadline-aware | Fair time-sharing, interactive responsiveness |
| **Timing** | Deterministic, bounded | Non-deterministic, best-effort |
| **Size** | Minimal, configurable | Large, feature-rich |
| **Architecture** | Drivers at app level | Drivers in kernel |
| **Overhead** | Minimal (predictability) | Higher (features, protection) |
| **Use Case** | Embedded, control systems | Desktop, servers |
| **Examples** | FreeRTOS, VxWorks | Linux, Windows, macOS |

**Key Insight**: RTOS trades features and fairness for timing guarantees.

### Comparison 2: Hard vs Soft Real-Time

| Aspect | Hard Real-Time | Soft Real-Time |
|--------|---------------|---------------|
| **Deadline Miss** | Catastrophic | Degrades quality |
| **Verification** | Formal proof required | Statistical analysis acceptable |
| **Scheduling** | Must guarantee deadlines | Best-effort, minimize misses |
| **Examples** | Airbag, flight control, medical | Video streaming, UI, gaming |
| **Cost Function** | Step to zero at deadline | Gradual decrease |
| **Tolerance** | Zero tolerance | Occasional misses OK |
| **Design** | Worst-case analysis | Average-case acceptable |

**Key Insight**: Hard real-time requires absolute guarantees; soft allows graceful degradation.

### Comparison 3: Processes vs Threads

| Aspect | Processes | Threads |
|--------|----------|---------|
| **Memory** | Separate address space | Shared memory space |
| **Context Switch** | Slow (full memory context) | Fast (registers only) |
| **Communication** | IPC mechanisms needed | Shared memory (direct) |
| **Isolation** | Protected from each other | Can interfere |
| **Creation** | Expensive | Cheap |
| **PCB** | One per process | Multiple per process |
| **Use in RTOS** | Less common | Very common |

**Key Insight**: Threads preferred in RTOS for lower overhead and easier communication.

### Comparison 4: Rate Monotonic Scheduling (RMS) vs Earliest Deadline First (EDF)

| Aspect | RMS | EDF |
|--------|-----|-----|
| **Priority** | Fixed (based on period) | Dynamic (based on deadline) |
| **Utilization Bound** | ~69% guaranteed | 100% guaranteed |
| **Optimality** | Optimal for fixed-priority | Optimal for preemptive |
| **Complexity** | Simple | Complex |
| **Runtime Overhead** | Low (no recalculation) | High (priority recalculation) |
| **Context Switches** | Fewer | More |
| **Predictability** | Very predictable | Less predictable |
| **Task Types** | Periodic with D=T | Periodic and aperiodic |
| **Analysis** | Draw schedule if U>69% | Simple: check U≤100% |
| **Implementation** | Easy | Harder |

**Key Insight**: RMS is simpler and more predictable; EDF achieves higher CPU utilization but at cost of complexity.

### Comparison 5: Preemptive vs Cooperative Scheduling

| Aspect | Preemptive | Cooperative |
|--------|-----------|-------------|
| **Task Switch** | Forced by system tick | Task explicitly yields |
| **Control** | Scheduler controls CPU | Tasks control CPU |
| **Real-Time** | Required for hard RT | Unsuitable for hard RT |
| **Responsiveness** | High-priority tasks run quickly | Blocked by misbehaving task |
| **Complexity** | Higher (context switching) | Lower |
| **Protection** | System protected | One bad task blocks all |
| **Use Case** | Hard real-time systems | Simple embedded, no strict deadlines |
| **Example** | FreeRTOS (default) | Arduino (loop-based) |

**Key Insight**: Preemptive scheduling essential for real-time guarantees but adds complexity.

### Comparison 6: delay() vs delayUntil()

| Aspect | delay(T) | delayUntil(&lastWake, T) |
|--------|----------|--------------------------|
| **Reference** | Current time | Last wakeup time |
| **Period** | T + execution_time | Exactly T |
| **Drift** | Accumulates over time | No drift |
| **Use Case** | One-time delays | Periodic execution |
| **Timing** | Relative | Absolute |
| **Implementation** | Block for T | Calculate next wake = last + T |

**Key Insight**: Use delayUntil() for precise periodic behavior; delay() causes timing drift.

### Comparison 7: Interrupt vs Preemption

| Aspect | Interrupt (IRQ) | Preemption (System Tick) |
|--------|----------------|-------------------------|
| **Trigger** | External event (hardware) | Timer (periodic) |
| **Timing** | Asynchronous, unpredictable | Synchronous, regular |
| **Handler** | ISR executes | Scheduler executes |
| **Return** | Usually to same task | To different task |
| **Purpose** | Handle external events | Enforce multitasking |
| **Duration** | Should be very short | Includes scheduling decision |
| **Task State Change** | Can unblock tasks | Can move running→ready |

**Key Insight**: Both use context switch mechanism but serve different purposes.

- All deadlines met
- Task 1 always preempts Task 2 when ready

### Example 2: RMS Utilization Bound Example

**Given:**
- Task 1: C1=2, T1=5
- Task 2: C2=3, T2=8
- Task 3: C3=1, T3=10

**Utilization:**
- U = 2/5 + 3/8 + 1/10 = 0.4 + 0.375 + 0.1 = 0.875 = 87.5%

### Example 3: EDF vs RMS Same Task Set

**Given:**
- Task 1: C1=3, T1=6
- Task 2: C2=4, T2=8

**Utilization:**
- U = 3/6 + 4/8 = 0.5 + 0.5 = 1.0 = 100%

**RMS Analysis:**
- Bound for n=2: 82.8%
- U = 100% > 82.8% → Not guaranteed
- Drawing schedule: Deadline miss occurs!
- **Not schedulable with RMS** ✗

**EDF Analysis:**
- U = 100% ≤ 100% → Schedulable ✓

- All deadlines met

### Example 4: Priority Inversion Problem

**Scenario:**
- Task H (high priority): Needs Resource R
- Task M (medium priority): Independent
- Task L (low priority): Holds Resource R

**Sequence:**
1. Task L starts, acquires Resource R
2. Task H arrives, needs R, blocks (L holds it)
3. Task M arrives, preempts L (M > L priority)
4. Task H blocked by lower-priority M! (priority inversion)

**Problem:**
- High-priority task H must wait for medium-priority M to finish
- Violates priority semantics
- Can cause H to miss deadline

**Solutions:**
- **Priority Inheritance**: L temporarily inherits H's priority while holding R
- **Priority Ceiling**: Resource has ceiling = highest priority of any task using it

### Example 5: Extended Interrupt Handling Pattern

**Application:** Serial data reception in embedded system

**Without Extended Handling:**
- ISR receives byte
- ISR processes byte
- ISR updates buffer
- ISR performs protocol handling
- ISR takes 500μs (blocks other interrupts!)

**With Extended Handling:**
- ISR receives byte (10μs)
- ISR adds to buffer
- ISR signals semaphore
- ISR returns (total: 20μs)
- Handler task unblocked
- Handler task processes data at lower priority
- Other interrupts not blocked

**Benefits:**
- Shorter ISR → better interrupt latency
- Complex processing scheduled normally
- System more responsive

### Example 6: Scheduling Anomaly - Faster CPU Causes Miss

**Original (Slow CPU):**
- Task H: Period=10, Computation=4, Priority=High
- Task L: Period=20, Computation=8 (3 in critical section), Priority=Low
- At slow speed: H arrives after L leaves critical section
- H preempts L immediately → H meets deadline ✓

**Faster CPU (2x speed):**
- Computation times halved: H=2, L=4 (1.5 in critical)
- L finishes normal code faster, enters critical section earlier
- H arrives while L in critical section
- H must wait for L to finish critical section
- H misses deadline ✗

**Lesson:**
- Faster hardware doesn't always improve real-time behavior
- Resource contention creates complex timing interactions

### Example 7: FreeRTOS Task Creation and Scheduling

**Code Example:**
```c
// Define two tasks
void Task1(void *param) {
    Time lastWake = xTaskGetTickCount();
    while(1) {
        // Do work
        vTaskDelayUntil(&lastWake, pdMS_TO_TICKS(100)); // 100ms period
    }
}

void Task2(void *param) {
    while(1) {
        // Do work
        vTaskDelay(pdMS_TO_TICKS(200)); // 200ms delay
    }
}

// Main function
int main(void) {
    // Create tasks with priorities
    xTaskCreate(Task1, "T1", 128, NULL, 2, NULL); // Priority 2
    xTaskCreate(Task2, "T2", 128, NULL, 1, NULL); // Priority 1

    // Start scheduler
    vTaskStartScheduler(); // Never returns
}
```

**Behavior:**
- Task1 higher priority (2 > 1) → always runs first when ready
- Task1 uses delayUntil() → precise 100ms period
- Task2 uses delay() → 200ms + execution time
- Scheduler automatically handles preemption via system tick

## Summary

**Real-Time Operating Systems (RTOS)** are specialized operating systems designed for embedded systems requiring **predictable timing behavior** and **deadline satisfaction**. Unlike general-purpose operating systems optimized for fairness and throughput, RTOSs prioritize **determinism**, **configurability**, and **real-time guarantees**.

**Key RTOS characteristics include:**
- Predictable timing with bounded execution times for all operations
- Deadline-aware scheduling algorithms
- Priority-based task management
- Minimal, configurable kernel focused on scheduling
- Support for both hard and soft real-time requirements

**Task scheduling in RTOS** uses a **three-state model** (Running, Ready, Blocked) with **preemptive context switching** driven by system tick interrupts. The scheduler manages task transitions, ensuring high-priority tasks run first and deadlines are met.

**Two fundamental scheduling algorithms** dominate real-time systems:
1. **Rate Monotonic Scheduling (RMS)**: Fixed priorities based on period (shorter period = higher priority). Simple and predictable, guarantees schedulability up to ~69% CPU utilization. Optimal among fixed-priority algorithms.

2. **Earliest Deadline First (EDF)**: Dynamic priorities based on deadlines (closest deadline = highest priority). Can achieve 100% CPU utilization, optimal for preemptive scheduling, but higher overhead.

**Schedulability analysis** determines whether all tasks can meet their deadlines by calculating **CPU utilization** (U = ΣCi/Ti) and comparing against algorithm-specific bounds. RMS requires drawing schedules above 69% utilization, while EDF has simple test: U ≤ 100%.

**Critical RTOS concepts** include context switching overhead, system tick configuration, synchronization primitives (semaphores), extended interrupt handling, priority inversion problems, and scheduling anomalies where faster hardware can surprisingly cause deadline misses due to timing interactions.

RTOSs enable embedded systems to meet strict timing requirements while managing hardware resources, handling interrupts, coordinating concurrent tasks, and supporting low-power modes—making them essential for safety-critical and time-critical applications like automotive control, medical devices, aerospace systems, and industrial automation.

## Possible Exam Questions

### Definitions & Technical Terms (Questions 1-25)

1. **What is a Real-Time Operating System (RTOS) and how does it differ from a general-purpose OS?**
   - RTOS is OS designed for real-time applications with predictable timing and deadline satisfaction
   - Differs from general-purpose OS: focuses on determinism vs fairness, minimal vs feature-rich, deadline-aware vs time-sharing

2. **Define the three task states in an RTOS and explain when each occurs.**
   - Running: task currently executing on CPU
   - Ready: task ready to execute but waiting for CPU
   - Blocked: task waiting for event/resource, not eligible for CPU

3. **What is preemption and why is it essential for real-time systems?**
   - Forcibly interrupting running task to allow another task to run
   - Essential because: ensures high-priority tasks get CPU quickly, enables priority-based scheduling, required for hard real-time guarantees

4. **Define context switch and what information must be saved/restored.**
   - Process of saving state of running task and restoring state of another
   - Must save/restore: CPU registers, program counter, stack pointer, status register

5. **What is the system tick and what role does it play in RTOS?**
   - Regular timer interrupt providing periodic "heartbeat" for scheduler
   - Roles: triggers preemption, allows scheduler to reassess priorities, provides time base for periodic tasks

6. **Define CPU utilization and provide the formula.**
   - Fraction of CPU time used by tasks: U = ΣCi/Ti
   - Critical metric for schedulability analysis

7. **What is the difference between lateness and tardiness?**
   - Lateness: Li = fi - di (can be negative if early)
   - Tardiness: Ei = max(0, Li) (always ≥ 0, measures how late)

8. **Define slack time and explain its significance.**
   - Maximum time task can be delayed before starting and still meet deadline: Xi = di - ai - Ci
   - Significance: indicates scheduling flexibility, Xi<0 means unschedulable

9. **What is a Process Control Block (PCB) and what does it contain?**
   - Data structure containing all information about a task
   - Contains: process state, ID, program counter, registers, priority, memory regions, stack/heap locations

10. **Define hard real-time, soft real-time, and firm real-time systems.**
    - Hard: missing deadline catastrophic (airbag, flight control)
    - Soft: occasional deadline misses tolerable, graceful degradation (video streaming)
    - Firm: late results worthless but no catastrophe (video frames)

11. **What is priority inversion and why is it problematic?**
    - High-priority task blocked by low-priority task holding needed resource
    - Problematic because: can cause high-priority task to miss deadline, violates priority semantics

12. **Define semaphore and describe its purpose in RTOS.**
    - Synchronization primitive for protecting critical sections and coordinating tasks
    - Binary (0/1) or counting (≥0), operations: P (wait/take) and V (signal/give)

13. **What is the critical moment in real-time scheduling?**
    - Time when all periodic tasks ready simultaneously (all have phase Φ=0)
    - Worst-case scenario for schedulability, analysis starts here

14. **Define hyperperiod and its relevance to scheduling.**
    - Least common multiple of all task periods: H = LCM(T1, T2, ..., Tn)
    - Relevance: schedule repeats every hyperperiod, must verify up to H for complete analysis

15. **What is extended interrupt handling and why is it used?**
    - Technique where ISR triggers task to handle non-critical processing
    - Used to: keep ISR minimal, allow complex processing in task context, improve responsiveness

16. **Explain the difference between dispatch and preempt in task state transitions.**
    - Dispatch: scheduler selects task from ready queue, moves to running (Ready→Running)
    - Preempt: forced interrupt of running task, moves to ready (Running→Ready)

17. **What is the difference between periodic and aperiodic tasks?**
    - Periodic: regular arrivals at fixed period Ti
    - Aperiodic: irregular, unpredictable arrival pattern, no fixed period

18. **Define sporadic task and how it differs from aperiodic.**
    - Aperiodic task with minimum inter-arrival time (bounded arrival rate)
    - Differs: sporadic has minimum interval enabling schedulability analysis

19. **What is configurability in RTOS and why is it important?**
    - Ability to include/exclude OS features based on application needs
    - Important: keeps OS lean, improves predictability, enables hard deadline guarantees

20. **Explain the difference between processes and threads in RTOS context.**
    - Process: separate memory space, heavyweight, slow context switch
    - Thread: shared memory within process, lightweight, fast context switch

21. **What are ISRs (Interrupt Service Routines) and what are their characteristics?**
    - Special functions executed in response to hardware interrupts
    - Characteristics: handle time-critical processing, should be short, can trigger task state changes

22. **Define response time and how it's calculated.**
    - Time from task arrival to completion: Ri = fi - ai
    - Includes waiting time and execution time

23. **What is meant by "optimal" in context of scheduling algorithms?**
    - RMS optimal for fixed-priority: if RMS can't schedule, no fixed-priority algorithm can
    - EDF optimal for preemptive: if EDF can't schedule, no preemptive algorithm can

24. **Explain the concept of determinism/predictability in RTOS.**
    - Ability to predict worst-case timing behavior
    - Requires bounded execution times for all operations (tasks, ISRs, system calls)

25. **What are the three essential RTOS requirements?**
    - Predictable timing (bounded execution times)
    - Meeting deadlines (deadline-aware scheduling)
    - Managing priorities (priority-based scheduling)

    - Faster execution changes timing of critical section entry

    - Demonstrates: faster hardware doesn't guarantee better real-time behavior

    - wait: Running→Blocked (task calls wait/delay/semaphore take)

    - Non real-time: constant value (no deadline)

40. **What are the assumptions of Rate Monotonic Scheduling?**
    - All threads on single CPU
    - Zero context switch time (negligible)
    - Independent threads (no resource sharing)
    - Constant computation time
    - Deadline = end of period (Di = Ti)
    - Shorter period = higher priority

42. **Explain the role of semaphores in extended interrupt handling.**
    - Handler task blocks waiting for semaphore token
    - ISR adds token to semaphore, unblocking handler
    - Handler becomes ready, runs at next scheduling point
    - Separates time-critical (ISR) from non-critical (task) processing

43. **Why is phase (Φ) important in schedulability analysis?**
    - Determines first arrival time of periodic task

    - Kernel-only (general-purpose): safer (untrusted apps), but more latency and less predictable
    - Embedded systems trade safety for performance and predictability

75. **Compare memory protection in RTOS vs general-purpose OS.**
    - General-purpose: strong protection (MPU/MMU), isolates untrusted applications
    - RTOS: often optional or omitted if all software trusted
    - Trade-off: protection adds overhead and complexity
    - Safety-critical RTOS may still need protection

### Application & Problem-Solving (Questions 76-100)

76. **Given three periodic tasks, how would you assign priorities using RMS?**
    - Identify periods: T1, T2, T3
    - Sort by period: smallest to largest
    - Assign priorities: shortest period gets highest priority
    - Example: T1=5, T2=10, T3=15 → Priority(T1) > Priority(T2) > Priority(T3)

77. **A task set has U=75%. Is it schedulable under RMS? Under EDF? Explain.**
    - RMS: U=75% > 69% → not guaranteed, must draw schedule to verify (may still be schedulable)
    - EDF: U=75% < 100% → guaranteed schedulable
    - EDF succeeds, RMS uncertain

78. **How would you verify schedulability for a task set with U=85% under RMS?**
    - U=85% > bound → not guaranteed by utilization test
    - Must draw schedule up to hyperperiod
    - Check every deadline of every task instance
    - If all met: schedulable, if any missed: not schedulable

79. **Calculate CPU utilization: T1(C=2, T=5), T2(C=3, T=10), T3(C=1, T=20).**
    - U = C1/T1 + C2/T2 + C3/T3
    - U = 2/5 + 3/10 + 1/20
    - U = 0.4 + 0.3 + 0.05 = 0.75 = 75%

80. **Design an extended interrupt handling system for a serial port receiving data.**
    - ISR: receive byte, add to buffer, signal semaphore, return (minimal time)
    - Handler task: blocks waiting for semaphore
    - When ISR signals: handler unblocks, processes buffer, performs protocol handling
    - Advantages: short ISR (good interrupt latency), complex processing schedulable

81. **A high-priority task is blocked by a low-priority task. How can you solve this?**
    - Priority inversion problem
    - Solution 1: Priority inheritance - low-priority task temporarily inherits high-priority
    - Solution 2: Priority ceiling - resource has ceiling = highest priority of users
    - Both prevent medium-priority tasks from blocking high-priority

82. **How would you implement precise 50ms periodic execution in RTOS?**
    - Use delayUntil() not delay()
    - Code: Time lastWake = now(); while(1) { do_work(); delayUntil(&lastWake, 50ms); }
    - OS tracks lastWake, calculates next wake = lastWake + 50ms
    - Maintains exact 50ms period regardless of execution time variation

83. **Calculate slack time: task arrives at t=10, needs C=5, deadline=20.**
    - X = d - a - C
    - X = 20 - 10 - 5 = 5
    - Task can be delayed up to 5 time units after arrival and still meet deadline

84. **Why might a system with 60% CPU utilization still miss deadlines?**
    - Utilization necessary but not sufficient
    - Possible reasons: resource contention, priority inversion, context switch overhead
    - Poor priority assignment, tasks with tight deadlines scheduled late
    - Blocking time not accounted for

85. **How would you reduce context switch overhead in an RTOS?**
    - Increase system tick period (fewer switches, but worse responsiveness)
    - Reduce number of tasks (fewer context switches)
    - Use cooperative scheduling for non-critical tasks
    - Optimize save/restore code
    - Use threads instead of processes

86. **Design a priority scheme for three tasks: UI (20ms period), Control (10ms), Logging (100ms).**
    - RMS: priority based on period
    - Control (10ms) highest priority
    - UI (20ms) medium priority
    - Logging (100ms) lowest priority
    - Shorter period = more critical = higher priority

87. **Calculate hyperperiod for tasks with periods 6, 8, and 12.**
    - H = LCM(6, 8, 12)
    - LCM(6, 8) = 24
    - LCM(24, 12) = 24
    - Hyperperiod = 24 time units

88. **How would you handle an aperiodic task in a periodic RMS schedule?**
    - Treat as sporadic with minimum inter-arrival time (if known)
    - Assign period = minimum inter-arrival time
    - Use priority based on this "period"
    - Alternative: background execution (lowest priority)

89. **What system tick frequency would you choose for tasks with 10ms minimum period?**
    - Tick should be fraction of shortest period: 1ms or 0.5ms
    - Too coarse: poor responsiveness (e.g., 10ms tick = no preemption within period)
    - Too fine: excessive overhead
    - Typical: 1/10 to 1/5 of shortest period → 1-2ms tick

90. **How would you optimize energy consumption in a battery-powered RTOS system?**
    - Align task periods to maximize idle time
    - Use delayUntil() for predictable sleep windows
    - Configure sleep modes in idle task
    - Minimize system tick frequency (less wakeups)
    - Batch processing to consolidate active periods

91. **A task misses its deadline. What are possible causes and solutions?**
    - Causes: CPU overload (U>100%), poor priority assignment, priority inversion, context switch overhead, blocking
    - Solutions: reduce computation times (optimize code), increase CPU speed, reduce number of tasks, improve priority assignment, fix priority inversion, analyze schedulability

92. **Design a scheduling scheme for: critical sensor (5ms), motor control (10ms), display (50ms).**
    - RMS priorities: Sensor highest (shortest period), Motor medium, Display lowest
    - Check schedulability: U = C_sensor/5 + C_motor/10 + C_display/50
    - If U ≤ 69%: guaranteed, if > 69%: draw schedule
    - Sensor always preempts others, motor preempts display

93. **How would you port a bare-metal application to use RTOS?**
    - Identify independent functions → create tasks for each
    - Replace manual timing loops with delayUntil()
    - Convert global variables to protected shared resources (semaphores)
    - Replace interrupt handlers with extended handling pattern
    - Configure system tick based on timing requirements

94. **Calculate tardiness: task finishes at t=25, deadline was t=20.**
    - L = f - d = 25 - 20 = 5 (lateness)
    - E = max(0, L) = max(0, 5) = 5 (tardiness)
    - Task is 5 time units late

95. **Why might increasing CPU speed cause a real-time system to fail?**
    - Scheduling anomaly: timing interactions change
    - Example: faster execution → task reaches critical section earlier
    - High-priority task now arrives during critical section (must wait)
    - At slower speed, arrives before critical section (preempts immediately)
    - Demonstrates: timing analysis must consider worst-case scenarios

96. **Design interrupt handling for multiple high-rate sensors (1kHz each).**
    - Use extended handling: ISR minimal (read sensor, add to buffer, signal)
    - One handler task per sensor or shared pool
    - Semaphore per sensor to unblock handler
    - Prevents long ISRs blocking other interrupts
    - Handlers schedulable with other tasks

97. **How would you implement rate groups (fast/slow tasks) in RTOS?**
    - Fast loop: high priority, short period (e.g., 1ms)
    - Slow loop: low priority, long period (e.g., 100ms)
    - RMS naturally creates rate groups (period-based priorities)
    - Fast tasks preempt slow tasks
    - Slow tasks run in gaps between fast activations

98. **A system needs guaranteed 99% CPU utilization. Which algorithm and why?**
    - Must use EDF (or another optimal dynamic algorithm)
    - RMS only guarantees up to ~69%
    - EDF can utilize 100% (99% safely schedulable)
    - Trade-off: EDF complexity and overhead acceptable for high utilization requirement

99. **How would you test real-time performance of an RTOS implementation?**
    - Measure context switch time (should be << tick period)
    - Verify schedulability with known task sets
    - Test deadline satisfaction under maximum load
    - Measure interrupt latency
    - Stress test with U near algorithm limits
    - Verify timing at critical moments

100. **Design a mixed criticality system: safety-critical control + non-critical logging.**
     - Assign highest priority to safety-critical tasks
     - Lowest priority to logging (background)
     - Ensure safety tasks schedulable even with U ignoring logging
     - Logging uses spare CPU capacity
     - Consider using different scheduling policies per group

### Advanced Topics (Questions 101-115)

101. **How does priority ceiling protocol prevent priority inversion?**
     - Each resource assigned ceiling = highest priority of any task using it
     - Task must raise priority to ceiling when acquiring resource
     - Prevents lower priority tasks from preempting while holding resource
     - Eliminates unbounded priority inversion

102. **Explain the relationship between schedulability analysis and design space exploration.**
     - DSE explores HW/SW partitioning options
     - Offloading tasks to hardware reduces Ci
     - Lower Ci improves CPU utilization
     - Schedulability analysis verifies timing feasibility of each design point
     - Trade-off: hardware cost vs guaranteed schedulability

103. **How would you handle transient overload in a soft real-time system?**
     - Use utility functions to prioritize most valuable tasks
     - Shed load: skip lower-value tasks
     - Degrade quality: reduce computation times
     - EDF with admission control
     - Queue lower-priority tasks for later execution

104. **What are the implications of non-zero phase (Φ ≠ 0) for schedulability?**
     - Different phases may avoid critical moment (all simultaneous)
     - Can improve schedulability vs synchronous release
     - But worst-case analysis assumes Φ=0 (critical moment)
     - Optimization: carefully chosen phases can reduce interference

105. **How does jitter affect real-time systems and how can it be managed?**
     - Jitter = variation in task arrival or completion time
     - Reduces slack time, complicates timing analysis
     - Management: add margins to WCET, use jitter-aware analysis
     - Minimize sources: consistent interrupt latency, bounded ISRs

106. **Explain how multi-core scheduling differs from single-core (preview of Lecture 14).**
     - Single-core: one running task, clear priority order
     - Multi-core: multiple simultaneous running tasks
     - New challenges: task partitioning vs migration, shared resource contention
     - Priority inversion more severe
     - Schedulability analysis more complex

107. **How would you integrate hardware acceleration (FPGA) with RTOS scheduling?**
     - Hardware operation as "task" with known computation time
     - Initiate hardware, block task waiting for completion
     - Hardware interrupt signals completion, unblocks task
     - Reduces effective Ci (faster hardware)
     - Improves CPU utilization for other tasks

108. **What is the role of worst-case execution time (WCET) analysis in real-time systems?**
     - WCET = upper bound on task execution time (Ci)
     - Essential for schedulability analysis
     - Methods: measurement, static analysis, hybrid
     - Must account for: caching, pipelining, interrupts
     - Safety margin often added to measured values

109. **How do cache effects complicate real-time analysis?**
     - Cache hits/misses create execution time variation
     - Context switches may invalidate cache (cold cache on resume)
     - WCET analysis must assume worst case (all misses)
     - Makes analysis pessimistic
     - Cache partitioning or locking can improve predictability

110. **Explain mode changes in real-time systems (e.g., startup vs normal operation).**
     - Different task sets for different modes
     - Mode change must be schedulable (transition period)
     - Analysis needed for: each mode independently, transition between modes
     - Example: startup mode loads configuration, normal mode performs control

111. **How would you verify that an RTOS meets certification requirements (e.g., DO-178C)?**
     - Formal verification of timing properties
     - Extensive testing (statement/branch coverage)
     - Traceable requirements to code
     - Qualified tools for compilation and analysis
     - Documentation of worst-case behaviors
     - RTOS may need to be certified (e.g., QNX, VxWorks)

112. **What are the challenges of resource sharing beyond simple semaphores?**
     - Nested critical sections (deadlock risk)
     - Multiple resources accessed in different orders
     - Priority inversion amplified with multiple resources
     - Solutions: resource access protocols (PIP, PCP, SRP)
     - Blocking time analysis becomes complex

113. **How does EDF handle tasks with D < T (deadline before end of period)?**
     - EDF directly uses absolute deadlines
     - Works naturally with any D ≤ T
     - Schedulability test more complex: U ≤ 1 insufficient
     - Must check: no point in time where demand exceeds capacity
     - More general than RMS assumption D = T

114. **Explain the concept of response time analysis for fixed-priority scheduling.**
     - Calculate worst-case response time for each task
     - Iterative method considering interference from higher-priority tasks
     - Ri = Ci + Σ(higher priority interference)
     - If Ri ≤ Di for all tasks: schedulable
     - More precise than utilization bound, accounts for blocking

115. **How would you debug timing problems in an RTOS application?**
     - Instrument code to log task switches, deadlines
     - Trace scheduler decisions
     - Measure actual execution times vs expected Ci
     - Check for priority inversion (unexpected blocking)
     - Verify system tick frequency appropriate
     - Logic analyzer to observe real-time behavior
     - Check for interrupt storms or excessive ISR time
